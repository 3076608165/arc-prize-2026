# Public record, second pass: what changed since 2026-09-19 (read 2026-09-23)

The first survey ([public-solutions-2026-09.md](public-solutions-2026-09.md))
concluded "no better public target exists" and ranked the model class as the only
lever. Four days later the same lineage has grown a small measurement community,
and two of its members have published experiments that bear directly on our
stuck score. Everything below was pulled and read today; the pulled notebooks
are in `experiments/intel-20260923/`.

## ARC-AGI-2: the 33.89 lineage is being instrumented in public

### `johntaylorai`'s swarm campaign (eight notebooks, 2026-09-19 → 09-22)

The most useful public work we have found in this competition. Each arm is the
same 33.89-baseline notebook with exactly one thing changed, which is the
discipline this campaign has been missing.

- **`swarm-arc2-numerics-control`** — the load-bearing claim: *"the original
  notebook as published cannot run today: the stale model path is why. Anyone
  currently scoring 33.89 is running a path-fixed variant."* Their control
  reverts `arc_solver.py` to the ORIGINAL baseline numerics (GPU-side logits
  patch removed) and predicts ~33.89 if the perfpatch's numerics are the
  difference, ~29.7 if the gap is the run environment — i.e. it is exactly the
  experiment that decides whether our 28.9-31.0 band or the public 33.89 is the
  real level of this notebook.
- **`swarm-arc2-budget-curve`** — `elapsed` recorded on every decoded candidate
  so one full-budget run reconstructs the score at any per-task cap; starter
  covers the full 120-task eval split in commit mode. Their measurement: 705 s
  available per task in rerun mode, a 1200 s cap, an 888 s observed mean, "so
  20-41% of test tasks are never attempted and score a certain zero". That is
  the number that would justify anytime scheduling.
- **`swarm-arc2-decorrelate-pilot`, `-adapt-arm`, `-arm-b2`** — widen the DFS
  bound (`max_score` `-log(0.2)` → `-log(0.05)`) to make candidates *diverse*
  rather than merely more likely, because "per-cell consensus produced 0 novel
  correct grids in 86 chances, so the 17 augmentations make the same mistakes".
  Same conclusion our own cell-vote arm reached on the other side (-6 tasks).
- **`swarm-arc2-legc-measure`, `-lb3389-baseline`** — the same Leg C induction
  idea as below, instrumented.

### `dalezhong/arc-agi-2-nvarc-plus-ckpt` — NVARC+ v2, a concrete better config

Two independent half-cost TTT passes whose candidate pools are merged, cheap-first
task order, a catch-up pass over tasks pass A never reached, `score_kgmon` over
the pooled candidates, and the invariant that **pass A's top-1 is always kept
among the two attempts** ("so the ensemble can never lose a task the single-pass
baseline would score"). Plus incremental `submission.json` checkpointing so a
crash keeps everything decoded so far. Rerun budget: `12h - 15min`.

### `koushikrudra/failed-in-aimo` — Leg C, and we already hold the source

Full source cached since 2026-09-10 in `agi2/out/refs/failed-in-aimo-20260910`
(diffed against the base in `refs/top-public-diff.txt`): a verified-induction
pre-pass that samples DSL programs with Qwen2.5-Coder-7B (4 L4 workers, 8
samples + one repair round), verifies each program against ALL train pairs in an
AST-whitelisted, torch-free, SIGALRM-bounded sandbox, and merges train-verified
outputs monotonically (attempt_1 = verified program output, base candidate
demoted to attempt_2). The author's own title says it failed in an AIMO run.

## What we did with this, and what we did not

**Adopted: two-pass pooled selection** (implemented today, `agi2/repro_nvarc.py`,
six tests in `agi2/test_two_pass.py`, pushed as ARC-AGI-2 kernel **version 12**).
Pass B is queued behind all of pass A with different augmentation seeds
(`seed=1+101·p`, `seed=2+103·p`) and its own candidate store; the submission cell
pools both stores but pins `attempt_1` to pass A's top-1. Monotone by
construction: a noisy pass B can only change `attempt_2`. Rationale is our own
data: byte-identical reruns land in 28.9-31.0, so a redraw is worth something,
and until now the only way to spend one was another day's slot.

**Rejected for now: anytime scheduling / cheap-first ordering.** Our own audit
(`coverage-benchmark16`, 1 h, full 120-task eval split, 4 workers, audit on)
finished 24 tasks at a mean of 554 s and a max of 1346 s. Four workers × 11.83 h
= 170k worker-seconds against 120 × 554 s ≈ 66k — about 2.5 passes of capacity,
which is why pass B fits at all. The "20-41% never attempted" claim needs a cost
distribution roughly twice as expensive as the 888 s mean the same notebook
reports. Cheap-first ordering is still free and worth taking if it ever becomes
measurable, but it is not the lever it is advertised as.

**Not attempted: Leg C.** It costs ~1 h of the 12 h wall (the base is
time-hungry), needs a 7B coder model attached offline, and the one public
datapoint is titled "failed". Cheaper to watch `swarm-arc2-legc-measure` than to
re-run it ourselves.

## How the high scores select an answer, from the field's own reports

Three layers, in descending order of how much code we can actually read.

**1. The public TTT lineage (us, Team BlackBox at 33.89, every 33.89 fork).**
Selection is a ranker over the per-task candidate pool, and the pool is what the
augmentations and decode passes leave behind. In the upstream notebook we run:

```python
def hashable(guess):                      # dedupe/most-agreement key: exact grid
    return tuple(map(tuple, guess))

def getter_kgmon(guesses):                # default ranker, run_selection_algo()
    return len(guesses) - np.mean([np.mean(g["score_aug"]) for g in guesses])

def getter_full_probmul_3(guesses, baseline=3):
    return sum(baseline - g["beam_score"] for g in guesses) \
         + np.mean([np.sum([baseline - s for s in g["score_aug"]]) for g in guesses])
```

`score_kgmon` = how many independent decodes emitted *this exact grid*, minus the
model's mean re-encoding score of it: consensus first, likelihood as tie-break.
`score_full_probmul_3` = generation likelihood plus verification likelihood.
`attempt_1` and `attempt_2` are the **top two of one ranking** (`fill_submission`
walks the ordered list), and the second ranker exists only in
`benchmark_selection_algos` — nobody in this family submits a different ranker
per attempt.

**2. What the strongest public team in that family reports** (madarshbb,
"Open-sourcing my work and analysis until now", discussion 729743, 2026-07-26):
multiple selection strategies apart from `score_kgmon` — "while some helped in CV,
it couldn't translate to LB"; a second decoding round with different seeds "didn't
move score"; NLL thresholds static and dynamic — "no statistically significant
move"; TRM candidates added to the pool — no meaningful gain (TRM ~10 on LB, too
weak to cross-reference, and "there are 1-2 puzzles qwen couldn't solve which TRM
could, but it is very difficult to leverage these tasks without the selection
strategy also letting go of puzzles which qwen successfully solved"); per-puzzle
loss plateaus, so extra TTT time is worth nothing. Their measured wins were all
*speed* (largest-puzzles-first queue) and *attribution* (batch-invariant ops via
`thinking-machines-lab/batch_invariant_ops` + cached per-puzzle adapters, at the
cost of being slow) — infrastructure for telling a real gain from TTFT
stochasticity, not score itself. `cpmpml`'s own comment in the same thread agrees
that batch-invariance is slow, and notes the cached-adapter trick as the way to
skip re-running TTFT.

This is the same conclusion our own dead list has: nine rankers (0, 0, −1),
per-cell voting (−6), 2B ensemble (oracle ceiling +2, no selector above 6/34),
identity demotion, shape filters. **Within this family, selection is a measured
dead lever.**

**3. Outside the family (55 → 83) nothing about selection is public.** Tufa Labs
(#1 on both boards), rabbithole, nvbanana and Yi-Chia Chen publish nothing
code-level for ARC-AGI-2. What is public from them concerns ARC-AGI-3, where the
question does not apply at all: the score is levels completed by an agent driving
the official arcade, so there is no per-answer selection step. Tufa's milestone-1
writeup (discussion 717133) describes the shape of that agent: Qwen 3.6 27B FP8 in
an inference harness, a Python tool for interacting with the game, and *continuous
context eviction* so it can keep playing indefinitely — i.e. the analogue of
selection is which observations the context keeps. Their milestone-1 submission
scored 1.21%; the same harness now reads 18.81. Yi-Chia Chen's public ARC-AGI-3
notebook (`threerabbits/submission-32b-fix4`) is a random-move baseline plus the
official plumbing (`arc_agi` wheel, `.env` offline-vs-rerun switch, `gateway:8001`,
`RESET` on `GAME_OVER`, 1000 moves, scorecard) — that plumbing, not the policy, is
what it contributes.

Consequence for us: stop buying selection tweaks. Both the field and our own logs
say the pool, not the ranker, is binding, and in this lineage the pool comes from
test-time training plus decode diversity — where the only unmeasured candidate is
a second *family* of candidates (Leg C) with its own exactness signal.

## Ranked next actions, each with what would falsify it
1. **`version 12` (two-pass) on the next slot.** Prediction: monotone but
   probably null. The field evidence below (a second decoding round with
   different seeds "didn't move score") downgrades this from "upside" to "free
   test of a public claim"; it still cannot lose a task pass A would have
   scored, because attempt_1 is pinned to pass A's top-1. Falsified as a win if
   it lands inside the 29.90 ± 0.64 band with pass B having run.
2. **Watch `swarm-arc2-numerics-control`.** If the original numerics read 33.89,
   the perfpatch itself is costing ~4 points and reverting it is a two-line
   change with a large expected gain. If they read ~29.7, the 33.89 is an
   environment artifact and the whole family's ceiling is what we already have.
3. **Cross-family diversity for `attempt_2`** (Leg C or a DSL search arm): the
   pool has +9 oracle headroom our selectors cannot reach, so a second family
   with its own exactness signal is the only remaining candidate on the
   selection side that has not been measured dead.
4. **ARC-AGI-3 stays the largest absolute upside and is still a lottery.** The
   board max is 18.81; our best draw is 0.27 and our agent is a CPU sweep. The
   June-30 milestone winner's harness is public (`mayakaripel/tufa-labs-duck-harness-june-30-milestone-winner`,
   Qwen3.6-27B-FP8 + tool harness + vLLM wheelhouse datasets), and the same
   family is being run publicly at 8B-32B scale (`yuriimuktarov/arc3-duck-qwen38-r16`,
   `ashwanidhukra/arc-agi3-qwq32b-v1`, `baopv051/xla-eval-harness-ours`). Porting
   it is days, not hours, and it is the only route from 0.27 to anything with a
   different order of magnitude.
5. **Largest-puzzles-first queue, staged for version 13** (`--largest-first` in
   `agi2/repro_nvarc.py`, implemented and tested today, deliberately NOT in
   version 12 so that a score move stays attributable to one change). It is
   scheduling only — same keys, same candidate pool — and it protects exactly
   what a second pass needs: today the queue is alphabetical, so the expensive
   tail is reached last and gets no pass B at all. Held to version 13 because the
   public report measures it as a speed win, not a score win; we have no reason
   to believe it moves the score, and mixing it into version 12 would hide that.
